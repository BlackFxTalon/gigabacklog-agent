# GigaBacklog Agent

## Идея проекта

**GigaBacklog Agent** — демонстрационный AI-агент для первичной обработки внутренних заявок и задач сервисного подразделения.

Агент получает неструктурированное описание проблемы, находит похожие обращения в локальной SQL-базе, определяет категорию и рекомендуемый приоритет, после чего возвращает валидированный структурированный результат и сохраняет историю обработки.

Проект предназначен для демонстрации навыков, релевантных вакансии разработчика ИИ-агентов в Сбере:

- Python;
- GigaChat;
- GigaChain/LangGraph;
- tool calling;
- структурированные результаты;
- SQL;
- обработка backlog;
- приоритизация задач;
- интеграция AI с корпоративными системами;
- контролируемое и проверяемое выполнение агентных действий.

> Проект является демонстрационным прототипом. Он не предназначен для обработки реальных банковских или персональных данных.

---

## Проблема

Сотрудники сервисных подразделений получают внутренние обращения в свободной форме. Перед передачей исполнителю заявку приходится вручную:

1. прочитать;
2. кратко сформулировать проблему;
3. определить категорию;
4. оценить масштаб влияния;
5. найти похожие обращения;
6. назначить предварительный приоритет;
7. запросить недостающие сведения;
8. предложить следующее действие.

GigaBacklog Agent автоматизирует первичную обработку, но не принимает окончательных управленческих решений без участия человека.

## Пользовательский сценарий

1. Пользователь запускает приложение одной командой.
2. CLI предлагает описать проблему свободным текстом.
3. Агент анализирует обращение.
4. GigaChat принимает решение вызвать инструмент `search_similar_requests`.
5. Инструмент выполняет ограниченный SQL-запрос к SQLite.
6. Найденные обращения возвращаются агенту.
7. Агент формирует структурированный JSON.
8. Результат проверяется Pydantic-моделью.
9. Входные данные, результат, статус и факт вызова инструмента сохраняются в SQLite.
10. CLI показывает пользователю вызов инструмента, итоговый JSON и идентификатор запуска.

---

## Почему это AI-агент

Проект не ограничивается одним запросом к языковой модели:

- модель получает цель и контекст;
- модель определяет необходимость вызова инструмента;
- инструмент выполняет контролируемое действие;
- результат инструмента возвращается модели;
- модель использует результат для итогового решения;
- ответ проверяется независимо от модели;
- история выполнения сохраняется для аудита.

LLM не получает произвольного доступа к базе данных. Единственная доступная операция — безопасный инструмент поиска похожих заявок.

## Компоненты

### `app/config.py`

- читает `GIGACHAT_CREDENTIALS`;
- проверяет наличие обязательной конфигурации;
- не содержит секретов в исходном коде.

### `app/database.py`

- создаёт таблицы SQLite;
- добавляет исторические заявки;
- ищет похожие обращения;
- сохраняет историю запусков агента.

### `app/models.py`

- содержит Pydantic-модель результата;
- определяет допустимые категории;
- определяет допустимые приоритеты;
- запрещает произвольную структуру финального ответа.

### `app/tools.py`

- содержит единственный агентный инструмент;
- предоставляет ограниченный доступ к поиску;
- не позволяет модели выполнять произвольный SQL.

### `app/agent.py`

- создаёт GigaChat-модель;
- регистрирует инструмент;
- запускает агентный цикл;
- получает итоговый ответ;
- выполняет Pydantic-валидацию;
- при необходимости запрашивает одно исправление результата.

### `app/__main__.py`

- запускает CLI;
- принимает текст заявки;
- показывает этапы выполнения;
- выводит итоговый JSON;
- сообщает идентификатор сохранённого запуска.

## Модель структурированного результата

```python
from enum import Enum

from pydantic import BaseModel, Field


class Category(str, Enum):
    access = "access"
    incident = "incident"
    consultation = "consultation"
    improvement = "improvement"
    other = "other"


class Priority(str, Enum):
    p1 = "P1"
    p2 = "P2"
    p3 = "P3"
    p4 = "P4"


class AffectedUsers(str, Enum):
    one = "one"
    several = "several"
    department = "department"
    organization = "organization"
    unknown = "unknown"


class RequestAnalysis(BaseModel):
    title: str = Field(min_length=5, max_length=120)
    summary: str = Field(min_length=10, max_length=500)
    category: Category
    priority: Priority
    reason: str
    affected_users: AffectedUsers
    missing_information: list[str]
    recommended_action: str
    similar_request_ids: list[int]
    requires_human_approval: bool = True
```

Финальный ответ считается корректным только после успешного выполнения:

```python
RequestAnalysis.model_validate_json(response)
```

## Инструмент агента

### Название

```text

```

### Сигнатура

```python
def search_similar_requests(query: str) -> str:
    """Find similar historical requests in the local database."""
```

### Назначение

Инструмент получает поисковую фразу от агента и возвращает до пяти похожих исторических обращений.

### Пример SQL-запроса

```sql
SELECT
    id,
    title,
    description,
    category,
    priority,
    resolution
FROM requests
WHERE
    title LIKE :pattern
    OR description LIKE :pattern
ORDER BY created_at DESC
LIMIT 5;
```

### Пример результата инструмента

```json
[
  {
    "id": 3,

    "category": "access",
    "priority": "P1",
    "resolution": "Откатили конфигурацию сервиса авторизации"
  }
]
```

## Схема базы данных

### Исторические заявки

```sql
CREATE TABLE IF NOT EXISTS requests (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    description TEXT NOT NULL,
    category TEXT NOT NULL,
    priority TEXT NOT NULL,
    resolution TEXT,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### История запусков агента

```sql
CREATE TABLE IF NOT EXISTS agent_runs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    raw_request TEXT NOT NULL,
    structured_result TEXT,
    tool_called INTEGER NOT NULL DEFAULT 0,
    status TEXT NOT NULL,
    error_message TEXT,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Для прототипа структурированный результат сохраняется в `structured_result` как JSON.

## Правила приоритизации

| Приоритет | Правило |
|---|---|
| `P1` | Остановлен критичный процесс, затронуто подразделение или вся организация |
| `P2` | Сильно нарушена работа нескольких пользователей, обходной путь отсутствует |
| `P3` | Проблема ограничена, существует обходной путь |
| `P4` | Консультация, улучшение или некритичная задача |

Модель обязана вернуть не только приоритет, но и его объяснение в поле `reason`.

Приоритет является рекомендацией. Окончательное решение остаётся за человеком, поэтому `requires_human_approval` по умолчанию равно `true`.
